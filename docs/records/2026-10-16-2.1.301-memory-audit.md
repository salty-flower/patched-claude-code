## Memory contract

| Concern | Upstream behavior retained |
| --- | --- |
| File structure | Separate topic memory files; `name`, `description`, nested `metadata.type` frontmatter; four types: user, feedback, project, reference; related-memory wikilinks |
| Meaning | Feedback records corrections and confirmed approaches; feedback/project bodies retain rationale and application guidance; project dates become absolute |
| Index | `MEMORY.md` contains concise one-line links, no frontmatter or memory bodies; index loading is capped; metadata and topical organization stay current |
| Writes | Check existing memories before creating another; update existing topic files; update/remove wrong or stale entries; fulfill explicit remember/forget requests subject to exclusions |
| Exclusions | Repository-derived structure, code conventions, git history, fixes already represented in code, CLAUDE.md content, and ephemeral conversation/task state |
| Verification | Revalidate recalled claims against current files/resources; current observations win; check named paths, functions, and flags before recommendations |
| Context authority | Lean/shared variants explicitly identify recalled system-reminder content as background rather than user instructions; full default rules require revalidation and trusting current observations, without that exact explicit sentence |
| Other persistence | Full rules distinguish plans/tasks for current work from durable memory |
| Runtime state | Actual project directory, connected stores and permissions, loaded index content, optional citation guidance, and runtime extra guidelines remain upstream-generated |

Index-free recall mode deliberately omits index-writing instructions and instead limits individual memory file size.
Shared-store variants distinguish personal/private memory from writable or read-only team stores and prohibit shared secrets.
Read-only variants prohibit saving rather than pretending writes persist.
Memory type detail may move behind the upstream `memory-types` skill gate.
These are existing upstream branches, not repository simplifications.

The native assembler strips colon suffixes before exposing IDs, so `memory:L:R` becomes `memory`.
These suffixes still select the text variant; selected-text hash validation detects changes within one ID.
Selectors are pinned to an exact target version and hash-bind explicit replacements/removals.
This audit does not promise permanent identifiers across versions.
Final request diagnostics, rather than this conditional source inventory, determine which sections were actually sent.

## Changes from 2.1.296

The long-form memory rule string literals are unchanged in the audited memory constructor region.
Frontmatter, index conventions, exclusions, deduplication, stale-memory correction, and reference verification remain upstream semantics.
The static/dynamic SDK memory split already existed in 2.1.296.
2.1.301 adds a model-gated lean hygiene rewrite, replacing the previous combined hygiene/background sentences with equivalent expanded wording.
The repository intentionally preserves that upstream choice; it does not impose one prose variant on every model.

## Verification boundary

`tools/test/helpers/memory-prompt-contract.ts` checks semantic anchors in final request text, with separate full and lean profiles and an explicit expected directory.
It tests more than a heading or path and does not infer memory integrity from locator counts.
Source review establishes the contracts above; captured request tests establish which branch ran.
The helper's standard profiles assume writable file memory with an index; shared-store, read-only, and index-free configurations need their own branch-specific assertions.
